# One-off payments and payment methods

**Implementation status:** hosted Stripe Checkout session creation, token metadata create/read/list/update/revoke, and signed event ingestion exist. There is no local one-off order/invoice creation use case or fulfillment orchestration; therefore a Checkout session alone does not sell a product or grant access. PowerTranz is disabled pending its merchant contract.

Use `StripeAdapter.createOneOffCheckout` for a hosted Stripe one-off flow. Create an internal pending invoice/order first, use its ID as the idempotency key/reference, and grant paid entitlements only after a verified payment event. A browser redirect is not proof of payment.

Payment methods are registered only after a provider returns a token bound to the intended customer. A trusted `financial:manage` actor calls `registerPaymentMethod` with `provider`, `tokenReference`, optional `brand`, `last4`, `expiresMonth`, and `expiresYear`. The same manager can update display metadata with `updatePaymentMethod`; the user can list/get and revoke methods. These service reads/returns omit the provider token. Revoke is a soft delete: preserve the row for audit/reconciliation, and detach it at the provider as a separate operation. A provider-side detach must also be reconciled locally. There is no default-method selection or provider detach adapter yet.

The service validates last four and expiry shape, but it does **not** verify that a token exists at Stripe or belongs to the correct customer. The caller must make that provider check before registration. Do not accept a client-supplied token as proof of ownership. The database stores no PAN, CVC/CVV, track data, cardholder authentication data, or raw provider payload.

For one-off sales, the missing workflow is: create an immutable pending order/invoice with lines and tax/discount snapshots; bind the local ID and provider Checkout session ID; redirect to Stripe; await `checkout.session.completed` with `payment_status=paid` or `checkout.session.async_payment_succeeded`; reconcile the amount, currency, and account against the provider; mark paid and grant the selected entitlement once. A failed or expired Checkout session must not fulfill. Stripe documents [asynchronous Checkout events](https://docs.stripe.com/payments/existing-customers?platform=web&ui=stripe-hosted), which are why a success redirect alone is insufficient.

PowerTranz offers a [hosted payment page](https://powertranz.com/payment-gateway/hosted-payment-page), but its [developer page](https://powertranz.com/developers) limits detailed integration documents to qualified merchants and partners. The public Swagger's sale/payment/capture/refund/query shapes are not enough to prove callback authenticity or token ownership. Do not turn a browser redirect into a paid invoice. Obtain the merchant-specific contract before adding its adapter.

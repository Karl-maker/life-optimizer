# Provider synchronization and webhooks

## Stripe

Inject `{ verifier: stripeAdapter, actor: syncAgent, sync: billingService }` into `createApiServer({ stripeWebhook })`. The route preserves the exact JSON text (64 KiB limit), verifies `Stripe-Signature` HMAC and a five-minute timestamp window, and passes a bounded event to `billing.applyProviderEvent`. The sync transaction inserts `(provider,eventId)` once, applies a matching local invoice transition, and appends audit and outbox events. A duplicate delivery returns 200 without another payment or grant. The Stripe endpoint is `/webhooks/stripe`; use a snapshot event destination. Thin events need a retrieval adapter before applying them.
To set collection and refund access policy, inject `sync: { applyProviderEvent: input => billing.applyProviderEvent({ ...input, dunningSchedule: { delaysSeconds: [3600, 86400], graceSeconds: 172800 }, revokeOnFullRefund: true }) }`. This policy is chosen by the host, not inferred from a Stripe failure event.

For a one-off Checkout sale, first issue and bind a local invoice to the returned Checkout session ID. A `checkout.session.completed` event fulfills only when `payment_status=paid` and `amount_total`, currency, and `payment_intent` match the invoice. `checkout.session.async_payment_succeeded` follows the same path. An unpaid session does not grant access. `invoice.paid` or `invoice.payment_succeeded` can settle a local invoice only if it is bound to that Stripe invoice ID and the event has the same validated fields. Failed events create a dunning attempt if the local invoice matches. Unmatched events are retained as generic provider events for reconciliation.

`createFinancialService.applyProviderEvent` is the older status-only sync. It no longer advances invoice state because doing so would bypass the payment ledger; use `billing.applyProviderEvent` for any product sold by this package. It still records provider events and can synchronize a bound subscription status. Do not treat a browser success URL or a provider status change alone as a paid invoice.

Configure Stripe to send relevant events: `checkout.session.completed`, `.async_payment_succeeded`, `.async_payment_failed`, `.expired`; `invoice.finalized`, `.finalization_failed`, `.paid`, `.payment_succeeded`, `.payment_failed`, `.payment_action_required`, `.overdue`, `.marked_uncollectible`, `.voided`; subscription created/updated/deleted/trial-ending; payment method attached/updated/detached; payment intent failed/requires-action; refund created/updated; and dispute created/closed. The handler **fulfills** confirmed payment events, **records dunning** for matched invoice failure events, **records a succeeded `refund.updated`** against a known payment with a credit note, and **marks a known `payment_method.detached`** locally. Pass `revokeOnFullRefund: true` through a configured sync wrapper if a full refund should revoke access; the default retains access. Other event types are durably recorded and need focused reconciliation handlers before they may change local state. Verify Stripe's current [event catalog](https://docs.stripe.com/api/events/types) and [webhook delivery guidance](https://docs.stripe.com/webhooks) when adding one.

Provider events can be repeated and reordered. Unique event IDs prevent exact replay; unique payment references prevent a second Event object from double charging a local invoice. For provider status changes, compare provider timestamps with `lastProviderEventAt` and fetch the current provider object when two events disagree. An HTTP 200 means the event was durably accepted, not that a notification was sent or every provider object was reconciled.

## PowerTranz

`/webhooks/powertranz` accepts a browser-mediated form `Response`. It is **not a signed webhook**. The flow is safe only because `createPowerTranzCheckout` matches a stored token hash and invoice data, then calls PowerTranz server to server and requires a matching approved result. This route must be injected only when the adapter and checkout service are configured. See [PowerTranz](./powertranz.md) for the exact lifecycle and recovery behavior. Do not log the raw form body, token, PAN token, redirect HTML, credentials, or provider response.

## Apple App Store and Google Play

`/webhooks/apple-app-store` accepts App Store Server Notifications V2. `AppleStoreAdapter` verifies the signed envelope and nested transaction with Apple's root chain, bundle/app identity and configured environment; `notificationUUID` deduplicates delivery. `/webhooks/google-play` accepts only authenticated Pub/Sub pushes. `GooglePlayAdapter` verifies the signed push OIDC JWT, exact audience and service-account email, then looks up the purchase token through the Play Developer API. Neither a client-submitted JWS string nor an RTDN body alone grants access. Both sync into `store_purchases`, then grant/revoke `entitlements.store_purchase_id` in the same audited transaction. See [in-app purchases](./in-app-purchases.md), [Apple setup](./setup-apple-app-store.md), and [Google setup](./setup-google-play.md).

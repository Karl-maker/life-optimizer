# Set up Apple App Store purchases

1. Create the in-app purchase or auto-renewable subscription in App Store Connect. Record its exact product ID (SKU). Create a matching local product and price, then map it with `store.mapProduct({ provider: "apple", sku, priceId, actor, audit })`. The price controls **access**, not the App Store's final customer charge.
2. Create an In-App Purchase API key in App Store Connect and obtain its issuer ID, key ID and `.p8` private key. Download the current Apple root certificates from [Apple PKI](https://www.apple.com/certificateauthority/) and mount their DER files on the server. Configure the bundle ID and numeric App Apple ID. Apple's [Node server library](https://github.com/apple/app-store-server-library-node) performs chain, app and environment verification.
3. Set `EDU_APPLE_BUNDLE_ID`, `EDU_APPLE_APP_ID`, `EDU_APPLE_ISSUER_ID`, `EDU_APPLE_KEY_ID`, `EDU_APPLE_PRIVATE_KEY_FILE`, and `EDU_APPLE_ROOT_CERT_FILES` (comma-separated paths). Set `EDU_APPLE_ALLOW_SANDBOX=true` for sandbox/TestFlight; use `false` if that listener must accept production only. The [API environment example](../../../packages/api/.env.example) shows the format. Secret files must be mounted with limited permissions, not committed or logged. `readStoreProviderConfiguration` validates and builds the adapter at startup, or emits `financial.provider.unavailable` if fields are missing.
4. In App Store Connect, set the **App Store Server Notifications V2** production URL to `https://<host>/webhooks/apple-app-store`; add the sandbox URL if testing. Apple may send sandbox notifications to the production URL when no sandbox URL is set, so align the listener's sandbox setting. Apple requires an HTTPS endpoint. Send a [test notification](https://developer.apple.com/documentation/appstoreserverapi/request-a-test-notification) and confirm an audited `TEST` notification arrives. See Apple's [setup guide](https://developer.apple.com/documentation/appstoreservernotifications/enabling-app-store-server-notifications).
5. Before opening StoreKit purchase, generate and persist a stable random UUID for this app account, bind `iap.apple.<uuid>` to its financial account, and pass the UUID as `appAccountToken`. After StoreKit returns a signed transaction, the authenticated app calls `POST /store-purchases/apple/claim` with `{ "signedTransaction": "<JWS>" }`. The server verifies and refreshes it through Apple's Get Transaction Info API before granting access. After the server confirms, finish the StoreKit transaction in the app.

The webhook verifies the V2 `signedPayload` and `signedTransactionInfo`. It stores the notification UUID once; transaction ID identifies the purchase and original transaction ID connects renewals. Follow `SUBSCRIBED`, `DID_RENEW`, `DID_FAIL_TO_RENEW`, `GRACE_PERIOD_EXPIRED`, `EXPIRED`, `REFUND`, `REFUND_REVERSED`, `REVOKE`, and `RENEWAL_EXTENDED`. `DID_CHANGE_RENEWAL_STATUS` does not immediately revoke a paid period. Other signed types are recorded, and a notification without transaction data is recorded without changing access. Apple documents the current [notification type meanings](https://developer.apple.com/documentation/appstoreservernotifications/notificationtype).

The service emits `financial.store-notification.received`, `financial.store-purchase.*`, entitlement grant/revoke, and billing failure or renewal events. See [events](./events.md). A missing `appAccountToken` cannot establish a first account claim; Family Sharing needs a separately designed ownership flow and is rejected. If notifications are missed, use Apple's [Get Notification History and transaction/subscription status APIs](https://developer.apple.com/documentation/appstoreserverapi) to reconcile, then pass verified snapshots through `store.sync` with a trusted actor. Do not decode a JWS without signature verification or trust the app's claimed SKU.

# Set up PowerTranz

1. Configure all eight `EDU_POWERTRANZ_*` fields shown in [`packages/api/.env.example`](../../../packages/api/.env.example): base URL, merchant ID/password, hosted page set/name, ISO currency, numeric currency code and exponent. `readFinancialConfiguration` logs `financial.provider.unavailable` when any field is absent. Keep credentials in host secrets.
2. Expose the merchant response URL `https://<host>/v1/webhooks/powertranz` and mount `powerTranzCallback: { checkout }` in `createApiServer`. This URL is a **browser return**, not a signed server webhook. The returned `Response` field alone never proves payment.
3. Issue and validate an open local invoice. Call `createPowerTranzCheckout.begin` with the invoice ID, user ID, response URL and 3DS policy. Render the returned `redirectData` only inside the hosted provider iframe. The checkout stores a hash of the SPI token and binds an independent transaction ID to the invoice.
4. The callback matches the stored token hash, invoice amount, currency, order/transaction IDs and 3DS result, then calls PowerTranz `/spi/Payment` server to server. Only a matching approved response records payment and grants entitlements. Duplicate callbacks cannot charge twice. Declines produce dunning events; an ambiguous in-flight transaction remains `processing` for query/reconciliation.

See the detailed [PowerTranz Sale guide](./powertranz.md) and supplied [`docs/powertranz`](../../../docs/powertranz/) contract. This integration supports the confirmed hosted **Sale** flow only. Refund, capture, void and card-on-file merchant request bodies were not established by those materials, so no provider calls for them are exposed. Configure operational reconciliation for a browser that never returns; there is no signed asynchronous PowerTranz webhook in this implementation.

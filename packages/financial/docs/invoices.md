# Invoices, tax snapshots, payment allocation, and fulfillment

Create a catalog price before issuing an invoice. Call `billing.issueInvoice({ actor, audit, userId, idempotencyKey, lines, couponCode?, dueAt?, subscriptionId? })`. Each line names an active `priceId`, positive `quantity`, and an integer `taxRateBps` from 0 to 10,000; optional service start/end dates describe the coverage period. The manager's `onBehalfOf` must equal `userId`. Repeating the idempotency key for the same account returns the same invoice. A key owned by another account fails.

Issuance copies the product name, product/price IDs, quantity, unit minor amount, subtotal, allocated discount, tax rate and amount, line total, and service period into `invoice_lines`. The invoice stores an auto-incrementing local serial number, currency, subtotal, discount, tax, total, issue/due/paid timestamps, and provider reference. All lines must use one currency. Tax is calculated on each line **after** discount using half-up rounding: `(taxableMinor * taxRateBps + 5000) / 10000`. Sum line taxes for the invoice tax total. The tax rate is an input snapshot; this package does not determine the correct jurisdiction or exemption.

For a paid one-off invoice, call `billing.bindInvoiceProvider` with the provider and its checkout/transaction reference, then wait for verified provider settlement. A trusted adapter calls `billing.recordPayment` with the invoice ID, provider, unique payment reference, exact minor amount and currency, and provider occurrence time. The provider must match the invoice binding. A duplicate reference is a no-op if the stored amount and invoice match; a conflicting reference fails. Payments cannot exceed the invoice total. Once paid in full, the same database transaction marks the invoice paid, creates grants for every price entitlement mapping, writes audit records, and enqueues `financial.fulfillment.completed`. Partial payments leave the invoice open and grant nothing. A zero-total invoice is fulfilled at issuance once, without a provider charge.

For Stripe Checkout, the preferred sync entry point is `billing.applyProviderEvent` with the signed and parsed `PaymentProviderEvent`. It requires the bound Checkout session ID, payment intent, `payment_status=paid`, matching `amount_total` and currency. The generic `financial.applyProviderEvent` only synchronizes status and must not be used to fulfill a sold product. For PowerTranz, use the hosted Sale workflow in [PowerTranz](./powertranz.md).

The local serial number is a stable database sequence; it is not a legally compliant invoice number by itself. Before issuing tax invoices in a jurisdiction, add immutable seller and buyer legal identities, addresses, tax IDs, place of supply, exemption evidence, credit-note numbering, and retention/export rules to a jurisdiction-specific invoicing layer. Once issued, correct amounts with a linked credit note; do not change historical lines.
